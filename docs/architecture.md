# 設計方針

Go + HTMLテンプレート + PostgreSQL（部分更新が必要になったらHTMX）のモジュラーモノリスとする。
Webと自動RSS取得を同じプロセス・Podで実行する。定期実行と1回分の取得処理は分ける。
将来のCronJobでは同じイメージの`reader fetch --due`を呼び出す。

## 境界のルール

1. モジュール間のimportは次の表だけを許可する。同じモジュール内は自由。
2. 非公開の実装は各モジュール配下の`internal/`に置く。Goコンパイラがアクセスを制限する。
3. テーブルは所有モジュールだけが操作する。モジュール別DBユーザーとスキーマへのGRANTで制限する。

| モジュール | 責務・所有データ | import可能な他モジュール |
| --- | --- | --- |
| feeds | 購読・取得状況 | なし |
| articles | 記事・本文・既読・お気に入り・閲覧イベント | なし |
| ingestion | RSS取得と登録の調整 | feeds、articles |
| search | 検索・将来の検索索引 | articles |

起動コードは`cmd/`に置き、各モジュールを接続する。
新しいモジュールや依存方向は、自動チェックの許可表を変更して追加する。
インターフェースや階層は必要になった時点で導入する。

## 自動チェック

`go test ./...`で依存方向を検査する。テストコードのimportも対象とする。
未知の内部パッケージへの依存も拒否する。検査対象は現在のビルド環境で有効なGoファイル。
`internal/`のアクセス制限はコンパイル時に検査される。
DB権限はComposeの統合テストで、他モジュールのテーブルへのアクセス拒否を確認する。

## 機能設計

- 購読解除後も取得した記事を保持する。
- 記事の重複はDBの一意制約で防ぎ、再取得で既読・お気に入りを上書きしない。
- 削除したRSS記事は削除日時を保持し、再取得で復活させない。
- 本文を保存し、検索索引はそこから再構築する。表示した記事の全文は自動取得し、RSS本文とは別に保存する。
- 最初は部分一致検索とし、日本語全文検索は導入時にPGroonga等を評価する。

将来のサービス分離はモジュール境界を単位に検討する。
分離時には通信・データ移行・障害対応の設計が別途必要になる。

## 自動取得

- `ingestion.RefreshDue`が1回分の処理を担当し、Web内のループと`fetch --due`が共用する。
- `feeds`がttl、HTTP検証子、最終成功日時、次回取得時刻を所有する。
- 自動取得は期限が来たフィードだけを処理する。待機時間は通常の間隔とttlの長い方。
- 手動取得は期限を待たないが、同じDBロックで自動取得との重複を防ぐ。
- ロック専用のDB接続を使い、HTTP取得中にDBトランザクションは保持しない。
- HTTP検証子は記事の保存が完了した後に更新する。途中失敗で未保存記事を取りこぼさないようにする。

## 記事の表示・全文取得

- `ingestion.FetchArticle`が既存の公開ネットワーク用HTTPクライアントでHTMLを取得・抽出する。
- `articles`が抽出本文・検索用テキスト・最終URL・取得日時を所有する。RSS更新では上書きしない。
- HTMLをテンプレートで表示する直前に許可リスト方式でサニタイズする。配信元のCSSやスクリプトは実行しない。
- 画像はブラウザーが配信元から直接読み込む。画像保存・プロキシ・ブラウザーによるJavaScript実行は行わない。

## 本文の自動取得待ち

- 本文ペインの表示通知で初回表示日時を記録し、本文が未取得なら取得待ちへ追加する。RSS更新や一括既読では取得待ちを増やさない。
- 表示通知ごとに `articles.article_views` に記録し、記事の最終表示日時を同じ処理で更新する。再送は表示IDで重複を防ぐ。既存の表示日時は履歴一覧に引き継ぐ。
- `articles`が取得待ち・再試行日時・エラー・2分間の取得リースを所有する。
- `ingestion.RefreshFullContent`が最大10件を逐次処理する。外部キューや別サービスは追加しない。
- RSS取得とは独立した取得待ちなので、304応答でも本文取得の再試行が進む。
- Web内の定期処理と`fetch --due`から共通の処理を呼ぶ。HTTP取得中にDBトランザクションを保持しない。
- 表示中の記事は軽量な状態確認APIを使い、取得の完了やエラー状態の変化に合わせて右カラムを更新する。

- 移行時に既存の未取得記事の取得予定を解除する。保存済み全文は保持する。
- 手動の本文取得ルートとボタンは設けず、自動取得と再試行に統一する。

## OPML

- XML解析・購読の一括登録・OPML生成は`feeds`が担当する。
- ファイル全体を検証してから、1つのDBトランザクションで既存購読へマージする。
- 登録済みの購読名・取得予定は変更せず、購読解除済みのURLは同じIDで再購読する。
- エクスポートは購読中のURLと名前だけを、安定した順序のOPML 2.0として生成する。
- ファイルはメモリ内で処理し、受け付けたXMLから外部エンティティやURLを取得しない。
