# 設計方針

Go、`net/http`、`html/template`、素のJavaScript、PostgreSQLで構成するモジュラーモノリスとする。
定期取得のスケジュールと1回分の取得処理を分ける。KubernetesではCronJobがWebと同じイメージの`reader fetch --due`を1分ごとに呼び出す。
WebとCronJobのイメージタグは `k8s/reader/kustomization.yaml` の `images.newTag` に置き、通常のリリースでは `kubectl apply -k k8s/reader` で適用する。スキーマ変更時は別途マイグレーションJobを実行する。

## レイヤー構成

| レイヤー | 責務 |
| --- | --- |
| 起動・設定 | `cmd/reader/main.go` がコマンドを選び、`config` から設定を読み、ストアとサービスを接続する。 |
| プレゼンテーション | `cmd/reader` のHTTPハンドラーがリクエストやフォームを解釈し、HTML・JSON、ページ送りリンクを生成する。 |
| アプリケーション | `workspace`、`reading`、`ingestion`、`search`、`feeds.SubscriptionService` が処理を調整する。 |
| ドメイン | `feeds` と `articles` が購読・記事の型と入力ルールを定義する。 |
| インフラ | `feeds/postgres` と `articles/postgres` が各スキーマのSQLを実行する。`ingestion/httpfetch` が外部HTTP通信と解析を担当する。 |

アプリケーション側が必要な操作をインターフェースで定義し、起動時に実装を渡す。PostgreSQLアダプターは所有モジュールの型を使い、取得アダプターは取得結果を `ingestion` の型で返す。

## 境界のルール

1. 内部パッケージ間のimportは次の表に従う。アダプターは依存関係の検査で独立した単位として扱う。
2. パッケージをまたいで呼び出す操作だけを公開し、実装の詳細はパッケージ内に置く。
3. テーブルは所有モジュールだけが操作する。モジュール別DBユーザーとスキーマへのGRANTで制限する。

| モジュール | 責務・所有データ | import可能な他モジュール |
| --- | --- | --- |
| feeds | 購読・取得状況 | なし |
| feeds/postgres | 購読・フォルダーのSQLと取得ロック | feeds |
| articles | 記事・本文・既読・お気に入り・閲覧イベント | なし |
| articles/postgres | 記事・検索・閲覧記録・本文取得リースのSQL | articles |
| config | コマンドごとの環境変数の読み込みと検証 | ingestion |
| ingestion | RSS取得と登録の調整 | feeds、articles |
| ingestion/httpfetch | 外部HTTP通信、RSS・Atomと記事本文の解析 | feeds、articles、ingestion |
| reading | 既読操作・閲覧記録・記事本文取得の調整 | articles |
| search | 検索・将来の検索索引 | articles |
| workspace | 記事一覧と購読サイドバーの表示データの組み立て | feeds、articles |

起動コードは`cmd/`に置き、各モジュールを接続する。
新しいモジュールや依存方向は、自動チェックの許可表を変更して追加する。
インターフェースや階層は必要になった時点で導入する。

## 自動チェック

`go test ./...`で依存方向を検査する。テストコードのimportも対象とする。
未知の内部パッケージへの依存も拒否する。検査対象は現在のビルド環境で有効なGoファイル。
`internal/`のアクセス制限はコンパイル時に検査される。
DB権限はComposeの統合テストで、他モジュールのテーブルへのアクセス拒否を確認する。

## 機能設計

- 購読解除後も取得した記事を保持する。
- 記事の重複はDBの一意制約で防ぎ、再取得で既読・お気に入りを上書きしない。
- 削除したRSS記事は削除日時を保持し、再取得で復活させない。
- 記事のタイトル、RSS本文と取得済み全文のテキストを部分一致検索の対象とする。表示した記事の全文は取得を試み、RSS本文とは別に保存する。

将来のサービス分離はモジュール境界を単位に検討する。
分離時には通信・データ移行・障害対応の設計が別途必要になる。

## 自動取得

- `ingestion.RefreshDue`が1回分の処理を担当し、`fetch --due`から呼び出す。
- `feeds` がTTL、HTTP検証子、最終成功日時、次回取得時刻を所有する。
- 自動取得は期限が来たフィードだけを処理する。次回取得までの間隔は基本値 `FETCH_INTERVAL`（既定30分）とフィードのTTLの長い方。
- 手動取得は期限を待たないが、同じDBロックで自動取得との重複を防ぐ。
- ロック専用のDB接続を使い、HTTP取得中にDBトランザクションは保持しない。
- HTTP検証子は記事の保存が完了した後に更新する。途中失敗で未保存記事を取りこぼさないようにする。
- 定期取得では個別の通信・解析エラーを購読の `last_error` に保存して処理を続ける。DB保存の失敗や実行全体のタイムアウトはジョブ失敗として扱う。

## 記事の表示・全文取得

- `ingestion/httpfetch` が公開ネットワーク用HTTPクライアントでHTMLを取得・抽出する。
- `articles/postgres` が抽出本文・検索用テキスト・最終URL・取得日時を `articles.full_contents` に保存する。RSS本文と本文取得状態は `articles.entries` に保持し、全文保存と取得リースの解除を同時に確定する。
- HTMLをテンプレートで表示する直前に許可リスト方式でサニタイズする。配信元のCSSやスクリプトは実行しない。
- 画像はブラウザーが配信元から直接読み込む。画像保存・プロキシ・ブラウザーによるJavaScript実行は行わない。

## 記事表示時の本文取得

- `reading` が閲覧の記録と全文取得を調整する。記事を開いて既読にする操作は独立して扱う。
- 本文ペインの表示通知で閲覧イベントと初回・最終表示日時を記録する。表示IDを再送した場合は閲覧イベントを重複登録しない。
- 全文が未取得で失敗記録がなければ、表示通知の処理で取得を試みる。複数の要求が重なった場合は記事単位の2分間のリースで重複取得を防ぐ。HTTP通信中はDBトランザクションを保持しない。
- 取得に失敗したら、画面に失敗と「本文を再取得」ボタンを表示する。失敗後の再取得はボタン操作で行い、閲覧履歴は増やさない。

## OPML

- `feeds.Subscription` は購読と取得予定を表す。購読登録後の初回取得は `feeds.SubscriptionService` が調整する。
- `feeds` がXML解析とOPML生成を担当し、`feeds/postgres` が購読の一括登録を担当する。
- ファイル全体を検証してから、1つのDBトランザクションで既存購読へマージする。
- 登録済みの購読名・取得予定は変更せず、購読解除済みのURLは同じIDで再購読する。
- エクスポートは購読中のURLと名前だけを、安定した順序のOPML 2.0として生成する。
- ファイルはメモリ内で処理し、受け付けたXMLから外部エンティティやURLを取得しない。
